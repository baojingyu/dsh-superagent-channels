# 003 执行

> 语言：[中文](003-execution.zh-CN.md) · [English](003-execution.md)

本文跟踪一个已被接受的工单，经过执行、投递和恢复的过程。它建立在 [001 领域模型](001-domain.md) 和 [002 授权](002-authorization.md) 之上。

## 工单阶段

每个开启的工单都有一个阶段，由它在等待什么决定。从上到下读表；第一个匹配的行胜出。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 把输入投递给执行器会话失败；2 秒后重试，之后按翻倍延迟重试直至一分钟，一次成功、新的派工或工单结束都会清除它 | Input undelivered |
| person / answer | 它有一个待人工决定 | Awaiting answer |
| person / review | 最新报告是 `ready` | Awaiting review |
| person / blocked, failed | 最新报告是 `blocked` 或 `failed`，且此后没有人的消息到达该工单 | Blocked · Failed |
| working / queued | 没有派工，或有一个待启动的派工 | Queued |
| idle | 最新报告是 `waiting`，或派工已结束 | Waiting for a Trigger |
| working | 其他所有情况 | Working |

`person` 阶段意味着工单在没有人工输入的情况下无法继续。新的人类消息会把 `blocked` 或 `failed` 的工单释放给它的执行器，因此它移动到下一个匹配的阶段，通常是 `working`。

`idle` 工单已完成它的轮次，且没有悬而未决的问题。已订阅线程上的触发可以继续它。

## 执行器

每个工单得到一个名为 `worker-<ticket id>` 的执行器会话，以及一个以工单短名命名的目录。目录创建在配置的执行根目录下，默认是 `<stateDir>/work`。

执行器会话以操作者的操作系统用户身份、无需审批地运行命令。它们的 `dsh-superagent-worker` 预设包含工作所需的工具，并在 5 秒后把前台 shell 命令转为后台任务。这让执行器能在下一步接收新消息，而不必等待长命令完成。

主会话使用 `dsh-superagent-router`，具有相同的 5 秒 shell 与作业等待限制，以及更小的路由工具集。会话保留创建时所选的预设。执行器子智能体使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作与执行器槽位

当一轮结束时仍有 shell 作业或子智能体在运行，工单保留它的执行器槽位并保持工作状态。它不会被报告为等待，主会话也收不到等待报告。已完成的作业或子智能体会在同一槽位中带着结果唤醒执行器。一旦某轮在无后台工作的情况下结束，执行器就正常报告等待。

每一轮结束后，后台工作最多有 30 分钟完成。到达该限制时，shell 作业被杀死，工单被报告为等待。报告包含执行器最后的话，以及哪些作业被杀、哪些子智能体仍在活动。子智能体允许继续。执行器在下一轮读取被杀作业的结果。

向人的移交会立即释放槽位，并让报告继续生效。这适用于 `ready` 报告或提问之后（除非此后又到达了其他输入），也适用于任何 `blocked` 或 `failed` 报告之后。

移交时，子智能体停止。shell 作业（例如供评审的服务器）可以继续运行直到派工结束。它们不占用槽位，也不受 30 分钟限制，后续轮次之后同样如此。它们的完成不会唤醒执行器；执行器在下一轮读取结果。

人也可以直接在执行器会话中书写来开启一轮。它的后台工作遵循同样的规则。

派工结束时，它的 shell 作业被杀死且不唤醒会话。它的子智能体被释放，它们唤醒的任何完成轮次都被丢弃。替换的派工及其等待中的输入会在该关闭完成之后启动。

在 DeepSeek Harness 进程内停止或重启插件，走同样的关闭路径。尚未进入会话历史的输入会被保留。关闭会为每个执行器的后台工作最多等待 10 秒；进程重启则直接终止该工作。在忙碌中被中断的派工会带着恢复说明重新启动。

执行器子智能体（包括嵌套的）使用 DeepSeek Harness 的 `standard` 预设，并具有执行器的权限。它们只保留执行器被允许的工作工具，并在工单结束时失去这些工具。在 `standard` 下，shell 命令在 60 秒后转入后台。子智能体的作业在其结束时被杀死。

### 准备工单目录

在第一次派工之前，如果工单目录不存在，prepare 命令会在执行根目录下用 `sh` 运行一次。它有十分钟完成。没有 prepare 命令时，执行器在空目录中启动。

命令失败会使工单失败并记录其输出。重试或人在该工单某个线程上的消息会再次尝试准备。典型命令使用 `git worktree` 创建一个检出。当拉取请求分支的最后一段路径与工单短名匹配时，该拉取请求属于该工单。

### 并发

工单从启动开始（包括准备阶段）就持有一个执行器槽位，或者从唤醒其空闲执行器的那次投递开始持有。它在整个活动轮次中同样持有该槽位。

配置的并发上限作用于这些槽位，另有一个额外槽位用于人的消息或状态请求。当普通槽位已满时，这种唤醒可以使用额外槽位，并在新启动之前取得下一个空闲槽位。因此新工作无法阻止人继续已有的工单。

其他输入（例如 CI 结果）等待普通槽位。启动会在 `working / queued` 中等待直到有槽位空闲。启动是并发进行的，因此缓慢的 prepare 命令只延迟它自己的工单。

### 执行变量

prepare 命令和执行器指令收到相同的执行变量。命令读取环境变量；执行器在其提示词中读取它们的值和描述。其中都不包含凭据。

| 变量 | 注册者 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`、`DSH_SUPERAGENT_NAME`、`DSH_SUPERAGENT_TICKET` | Executor | 工单的目录、短名和 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | Executor | 执行器不可运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源所监视的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`、`DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`、`DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 启动该工单的 Issue 或拉取请求，以及当它是拉取请求时的 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`、`DSH_SUPERAGENT_FEISHU_CHAT` | Feishu | 机器人，以及启动该工单的群 |

工单特定的值来自它的目录和起始触发。其他值来自当前部署设置。只有面板能更改执行环境设置；发给主会话的文本无法更改已配置的 shell 命令。

执行器通过智能体账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书。被阻止的命令在按名称调用时失败。

这些包装脚本和目录建立的是默认值，而不是安全边界。执行器仍然可以通过绝对路径执行程序。

## 合并

自动合并由 **Delivery requirements** 提示词管控。宿主没有针对合并的专门决策逻辑。

默认情况下，执行器永不以智能体账号启用自动合并：GitHub 会把合并归因于启用它的那个人。交付要求必须指定另一个账号的 CLI 用于合并。没有指定时，由人来合并拉取请求。

默认指令只允许为工单开启的拉取请求启用自动合并，且要求它已就绪、必需批准覆盖 head 提交、新增加删除合计少于 200 行。在推送另一个修订之前，执行器会撤回自动合并。

没有正文的评审（例如批准）也会作为触发到达，并能唤醒正在等待评审的执行器。这些指令管控的是智能体，而不是 GitHub 的合并规则。要强制批准，请在分支保护中要求批准并清除过期批准。省略合并 CLI 或删除自动合并段落即可要求人工合并。

## 工单如何结束

- **就绪但没有拉取请求：** `ready` 报告使工单以已完成结束。
- **无事可做：** 执行器发现没有人需要行动的工作（例如请求无法复现或已被取代）时，报告 `dropped`。工单在没有消息的情况下结束，除非命中的规则要求一条消息，而人之后在其线程上的消息会恢复它。
### 拉取请求

一旦执行器报告了工单起始所在的拉取请求，工单就跟随它。它也跟随从它的分支开启的每个拉取请求，条件是执行器已报告或 GitHub 来源已发现。重新开启的拉取请求会再次被跟随。

当它开启的所有拉取请求都不再处于开启状态时，工单就完成了。如果它没有开启任何拉取请求，那么它跟随的所有拉取请求都必须已关闭。然后它以最后一次相关关闭的结果结束，并保留它的订阅，允许之后的人类评论恢复它。

当恢复、重试或恢复的工作尚未完成时，关闭不会结束工单。如果执行器确认或回答了它拥有的某条跟进，但此后尚未做出非进展报告、或在读取该消息后结束一轮，它同样会等待。之后的一份 `ready` 报告在满足同一拉取请求完成规则后结束工单。

聊天渠道会收到一条关于拉取请求结果的最终通知。GitHub 本身已在拉取请求上显示该结果。移除工单对某个拉取请求的订阅，也会让它停止跟随该拉取请求。

因此，「等待评审」意味着带拉取请求的 `ready` 报告。

### 跟进与上下文线程

执行器决定其工单自己线程上的人类跟进。它处理范围内的请求，并交回超出范围或属于其他工单的请求。一旦没有执行器拥有该消息，它就变为主会话的候选。除此之外，主会话只能按人的要求停止工作来处置该跟进。

输入在会话把它纳入某个步骤、并随后报告或结束一轮之后算作已读。工单结束时，未读且未被确认、未回答、未交回的消息回到评估，如 [002 授权](002-authorization.md) 所述。已读但未处置的消息（例如致谢）不会回到评估。

仅作上下文跟随的线程仍会投递消息，但不给工单对人工跟进的归属，也不恢复已结束的工单。那些消息可以被独立研判。

只要有一个在役工单订阅，来源就会轮询已订阅的线程，并在最后一个触发与订阅工单结束两者中较晚者之后继续两周。此后，消息只通过普通入口到达：GitHub 通知或飞书实时事件。

## 失败与恢复

### 执行器受阻或失败

当执行器会话报告 `blocked` 或 `failed`，或启动失败或出错（记录为 `failed`）时，工单不接受任何自动输入。

模型提供方或网络的瞬时失败、HTTP 408、429 或 5xx，或被拒绝、重置、超时的连接，会先重试三次，退避时间递增：启动会再次运行，轮次失败的执行器被告知继续；失败的 prepare 命令不再重试。

一旦失败，CI 和机器人消息会记录在工单上，但不被投递，也不唤醒会话。

它的工具仍然可用，因此人可以直接在会话中继续。

失败的启动不会自行重试。

人的消息、之后一份既非 `blocked` 也非 `failed` 的报告，或一次重试，都会解除该保持状态。

该状态由存储的报告和输入推算得出，因此重启后仍然保持。
### 重试

在开启的工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：新的派工会再次启动其执行器并接收等待中的输入，这是针对每一种情况的补救手段。

一旦人的消息到达受阻或失败的工单，执行器就拥有了该消息，因此工单显示为工作中，或在失败的启动重新开始时显示为排队中，并且不提供重试，除非投递该消息失败。

重试会结束当前派工，并在同一个执行器会话、目录、分支和拉取请求中启动新的派工。

执行器模型只在会话创建时生效；已存在的会话保留它的模型。
### 重启

运行中的派工以「host restarted」结束，新的派工带着恢复说明启动，该说明告诉执行器在重复任何外部操作之前先检查它的目录、git 历史和 GitHub，最旧的工单优先。

处于等待、就绪、受阻或失败状态的派工保持原样，除非在该报告之后有输入到达，那样它们也会重新启动。

会话、目录、订阅、待处理消息以及下文所述的已存储工作都能在重启后存活，每个执行器会话纳入其历史的消息记录同样如此：某个步骤在认领消息之后、调用模型之前把它们纳入历史——被重启切断的轮次所纳入的消息，在随后出现一份报告或一轮结束之后算作已读；而某个步骤已认领、但在进入历史之前被取消或错误切断的消息算作未读。

重试或重启会把投递给被替换派工、但其执行器会话未纳入的那些消息再次交给新派工，这些消息可能因取消或被切断的步骤而丢失；仍留在会话中等待的一份副本（由重启保留或跨崩溃持久化）会在新派工的第一条消息之前被取出，因此新的投递是唯一的副本。
### 已存储的工作

dsh-superagent 在决定之后要做的事（例如把候选、跟进或报告转达给主会话、启动派工或投递输入）会先被存储，然后再执行。

转达或投递失败（例如无法到达其会话）时，会在 2 秒后重试，之后按翻倍延迟重试直至一分钟；启动失败则使其工单失败，除非该失败是上文所述的瞬时失败。

每一类工作只有在连续三次失败之后，才会在概览的系统问题中报告错误；投递输入失败则改为显示在其工单上。

发往主会话的转达保持顺序，通知同样如此；一次失败会挡住同类中较晚的那些。
### 来源失败

GitHub 来源会分别读取每个 Issue、拉取请求和线程：读取失败会把错误保留在其线程上，在下一次轮询时再次读取，并计入来源的一次错误，默认在连续三次轮询失败后由来源报告；任何一次成功的轮询都会重置计数。

当智能体失去对私有仓库的访问权限时，GitHub 也会返回 404，因此 404 会重试。

一个已被通知但读取持续失败的 Issue 或拉取请求，会在首次读取失败一天后被丢弃，若 GitHub 报告它已删除则立即丢弃；此后它不再导致轮询失败，其线程保留该错误，来源的状态会点名它。

它的读取位置保持在原处，因此之后的通知或对其线程的轮询会读到失败读取所遗漏的内容。

飞书事件消费者会报告每一次失败，对已订阅话题的轮询会把每次失败保留在其线程上。

GitHub 列表或飞书页面中的格式错误条目会被跳过，来源的状态会把它计数。
### 渠道失败

出站消息作为已存储的工作被存储并发送，从 5 秒开始按翻倍退避重试，最多到 300。

一个工单发往同一个会话的消息按排队顺序发出，因此它的确认先于之后的回答或结果：当同一工单发往同一会话的较早消息尚未发出时，后续消息会等待，直到那条消息连续三次失败并显示为问题。

其他工单的消息，以及不属于任何工单的消息，不会等它。

有失败尝试的消息在发出或被撤回之前是一个系统问题。

只有当来源不再监听该会话，或来源回答该会话永远无法接收它时，消息才会被丢弃；当来源关闭时，消息等待。

GitHub 上已删除的 Issue 或已锁定的会话，以及飞书上被撤回或飞书已找不到的消息，来源会给出上述回答。

对已不存在的评审评论的回复，改为发往拉取请求的会话。

被丢弃的消息保留它的记录，包括丢弃时间、原因以及它所服务的工单，因此它永不会再次排队；被丢弃的确认读作已丢弃，而不是已发送。
### 暂停处理

停止派发、新的评估、评估超时、输入投递和回复；已经在进行的启动会等到处理恢复。

来源继续记录触发，正在运行的执行器轮次不被打断。

人发给已结束工单的消息会等待：暂停后的第一遍处理会恢复该工单，前提是它的授权在当时策略下仍然成立。

进行中的评估在暂停期间不会过期；它的截止时间按暂停时长向后顺延。
### 无效配置

被其种类拒绝的已存储来源配置会停用该来源实例。
