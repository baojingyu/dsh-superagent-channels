# 002 授权

> 语言：[中文](002-authorization.zh-CN.md) · [English](002-authorization.md)

授权决定谁可以启动工作，以及该工作可以包含什么。本文建立在 [001 领域模型](001-domain.md) 之上。

宿主强制实施白名单、规则和授权。消息、评论和引用的文档都是决定的输入；它们不能改变那些权限。

## 触发的两条路径

### 评估：决定是否启动工作

来源记录一条消息是否指向智能体：`mention` 表示提及机器人或智能体账号，`direct` 表示私聊消息。准入检查发送者和该来源的策略：

- 白名单上的人如果指向智能体，就构成明确请求。
- 人在已有工单的线程上的跟进，按下文规则处理。
- 其他人类消息按它们所在接收范围的准入表处理。
- 来源机器人名单上的机器人可以产生推断候选，永不产生明确请求。其他机器人不被准入。

### 订阅：继续已有的工作

已订阅线程上的每条消息都会作为上下文到达其已订阅的工单，包括来自机器人和 CI 的消息。这种投递绕过准入，也不授予任何新权限。每个工单仍然受其授权限制。

人在工单自己线程上的消息，由该工单的执行器决定。主会话把一条消息附加到某个工单时同样如此。当执行器拥有该消息时，它不经过评估，也得不到决定。每个执行器要么在其工单范围内处理该请求，要么把它交回以便路由到别处。

只要工单在役，归属关系就持续存在，即使有人移除了它的订阅。它也覆盖那些未被人停止、并且有待处理消息可将其恢复的已结束工单。

主会话会收到跟进通知。当执行器拥有该消息时，主会话只能按人的要求停止工作；接受、附加、忽略和重新排队都会被拒绝。停止仍然要通过准入，强度为下文所述的跟进强度。

### 交回与释放跟进

执行器在请求超出工单范围的工作、或消息属于另一个工单时，交回一次。工单保留它的订阅。如果被附加的线程无关，执行器交回它在那里拥有的消息。

只有当没有任何工单仍然拥有该消息时，它才进入一次新的评估。它的候选包含执行器给出的理由。准入把它当作该线程上的普通消息来判断，主会话可以接受它、把它附加到别处或忽略它。交回一条工单并不拥有的消息（例如机器人消息，或人已经发给评估的消息）不会排队任何东西。

工单结束时，它会释放其执行器未读取或未处理完的跟进。这包括从未投递给执行器的消息，以及在它最后一份报告或轮次结束之后投递、而执行器既未确认、未回答、也未交回的消息。每条被释放的消息在没有其他工单拥有它时进入评估。停止只结束被停止工单的工作。

被停止的工单不会把它的停止消息再次发给评估，除非另一个工单把它交回。停止它的主会话可以把消息剩余部分作为新工作接受。

人可以从面板把一条已被拥有的跟进发给评估。如果主会话随后把它附加回一个在役工单，执行器会再次收到它。当没有任何有效判断覆盖该消息时，面板也会提供重新评估。

### 仅作上下文的订阅

执行器可以为获取上下文而跟随相关线程，例如另一个 Issue 或拉取请求。那里的消息会到达工单，但不授予权限，也不带来跟进强度。那里的人类消息不会恢复已结束的工单，除非主会话附加了来自该线程的一条消息。主会话关于其他工作的说明也只是上下文。

未到达任何工单的人类消息（包括其工单被人停止的线程）走评估路径。机器人消息独立于它们对已订阅工单的投递，也走该路径。

## 强度

| 强度 | 情形 |
| --- | --- |
| explicit | 名单上的人指向智能体，或在已有工单的线程上跟进；准入表中设为明确请求的单元格 |
| inferred | 不在名单上的人在已有工单的线程上跟进，除非其准入表单元格是明确；准入表中设为推断候选的单元格；来源机器人名单上的机器人发出的、指向智能体的消息，或到达来源接收所有消息之处的消息 |
| not admitted | 其他任何机器人的消息、准入表忽略的一切，以及接单模式为 `off` 时的所有推断情形 |

对于不在名单上的人，明确的准入单元格优先，即使在已有工单的线程上也有效，并且在任何接单模式下都成立。否则其跟进为推断，在 `off` 模式下不被准入。仅在上下文中被跟随的线程上的消息，使用准入表而不是跟进强度。

## 准入

每个来源的策略都有一张准入表。它的行是接收范围：

- **飞书：** 每个已配置的群、机器人从中收到提及的其他群，以及私聊。只有在飞书卡片上把 **其他群** 设为 **仅 @** 时，其他群才会被接收。
- **GitHub：** 新 Issue、新拉取请求、评论以及默认分支的 CI。

一行最多有三个单元格。每个单元格决定一条消息成为明确请求、推断候选还是什么都不成为：

| 单元格 | 可选值 | 默认 |
| --- | --- | --- |
| 名单内，未指向智能体 | inferred、ignore | inferred |
| 名单外，指向智能体 | explicit、inferred、ignore | ignore |
| 名单外，未指向智能体 | inferred、ignore | ignore |

针对未指向消息的单元格，只在来源接收所有消息的地方可用，例如设为 **全部消息** 的飞书群，或开启了接收全部开关的 GitHub 范围。CI 结果没有发送者，因此它的行只提供最后一个单元格。机器人消息使用机器人名单，而不是这些单元格。

把「名单外且指向」单元格设为 explicit，可以让该范围内的任何人通过提及智能体来请求工作。这对专门的客服群可能有用。推断候选仍然取决于接单模式。跟进通常绕过此表，但 explicit 单元格仍然授予明确强度。

准入表是策略版本的一部分。弱化某个单元格不会立即停止按其接受的在途工单。当这些工单在恢复之前被重新校验时，它可以撤销它们的授权。

### 机器人与自动评审者

宿主把 GitHub App、以 `[bot]` 结尾的登录名以及飞书机器人识别为机器人。来源可以列出诸如 `dependabot[bot]` 的机器人，它们的消息可以成为推断候选。它们必须指向智能体，或在接收所有消息的范围内发帖。它们不能发出明确请求，也不能停止工单。

使用普通账号的自动评审者，对宿主而言算作人。它的评论会到达已订阅的工单并产生跟进通知。团队提示词文本必须把这类账号标记为自动评审者。

## 路由候选

主会话用 `orchestrator_route` 路由明确候选。一次调用可以包含多个接受、附加、停止或忽略的决定。每一项独立处理：某一项被拒绝或缺少字段，不会阻止其他项执行。

推断候选通常需要完整研判。有一个捷径：如果它的卡片明显不触及任何已启用的规则，例如普通闲聊或无关讨论，主会话可以直接忽略它。该决定记录 `ignoredFromCard`，以区别于按规则研判。主会话在其策略提示词段落中读取已启用的规则。

接受推断候选始终需要研判。直接接受会拒绝准入未认定为明确的触发。

## 接单模式与规则

接单模式是策略的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 推断出来的东西都不会成为候选，例如未指向的消息、机器人的消息，或名单外人员的跟进 |
| `observe`（默认） | 对推断候选进行研判；正向研判被记录为标记「would accept」的忽略，不接单 |
| `auto` | 对推断候选的正向研判会接受它 |

明确请求在任何模式下都有效。从 `observe` 开始，在审阅记录下来的决定之后再切换到 `auto`。每次研判都会对每条已启用的规则恰好判断一次，无论是否命中。主动接受要求至少命中一条规则。

每条规则描述一种主动工作。工单的授权记录命中的规则，其执行器会收到这些规则的名称和说明。

对该工单而言，规则中的流程与沟通要求覆盖默认值。静默规则可以抑制确认；评审规则可以指定必需的评审者和合并前的批准。适用于所有工单的要求应写在团队提示词段落中。

## 策略版本

规则、接单模式以及每个来源的策略共同构成策略版本。每个授权都记录它被接受时所依据的版本。

版本变更会丢弃正在运行的评估并重新排队它们的触发。它还会向每个受影响在役工单发送一条策略变更输入。该输入说明是否：

- 命中的规则发生了变化（包括其新文本），或不再适用；
- 请求者可能不再能启动工作；或
- 主动工作不再被接受，例如因为模式从 `auto` 改变了。

未受影响的工单不会收到通知。该变更不会立即撤销在役工单的授权。

来源配置与策略是分开的。它控制什么进入系统：读取哪些群，以及某个范围是接收全部消息还是仅接收提及。授权记录它的来源和接收范围。恢复需要来源仍然监听该线程，但不要求它仍然接收那里的每条消息。

当来源关闭时，回复会等待。如果来源不再监听其目的地，回复会被丢弃。

关于执行器可以用自己的结果做什么的条件（例如何时可以合并），不决定谁可以授权工作。它属于智能体的指令，而不属于策略。

## 恢复与停止

已结束的工单保留它的授权。人在它自己某个线程上的消息可以在没有新评估或新决定的情况下恢复同一工作，无论发送者是谁。机器人和 CI 不会唤醒已结束的工单。执行器决定该请求是否符合范围，若不符合则结束该轮。

只有三种操作会改变授权：接受创建它，人的停止撤回它，重新校验失败撤销它。被人停止的工单保持结束，不再接收任何东西。在那里请求工作需要新的接受。

### 恢复前的重新校验

来源必须仍然监听原始线程。其余检查取决于授权的依据：

- 明确的跟进授权通过。
- 推断的授权需要 `auto` 模式，且其命中的规则仍然启用。
- 由表格单元格准入的授权，必须在今天的表格和发送者成员关系下仍能获得至少其原始强度。因此，把发送者从名单中移除，可能撤销通过「名单内发送者」单元格接受的授权。
- 机器人的授权要求该机器人仍在来源的机器人名单上。推断的表格授权和机器人授权还需要 `auto` 模式以及命中的规则已启用。
- 其他授权要求发送者仍在来源的白名单上。

如果重新校验失败，工单保持结束，不接收它的任何等待消息。每条消息都被视为未到达任何工单；如果没有其他工单拥有它，它就进入评估。主会话不会被告知它到达了执行器。处理暂停之后同样如此。附加到该工单会被拒绝，进一步工作需要新的接受。

- **人在线程里说「stop」是一个普通触发，** 由评估决定停止。执行器不能声明某人要求它停止。
- **面板中的停止是一条命令。** 它直接作用于工单，并记录为手动停止。
- **等待类条件属于来源。** 例如「N 小时无处理人」这样的条件会是一个自行等待并再次检查的来源；评估从不等待。

## 评估未完成时

时限从候选到达主会话时开始。等待投递所花的时间不计入，未投递的候选永不过期。

超时的评估会重新排队它的触发以便再次尝试。连续两次重试之后，第三次超时记录为 `unavailable`。研判失败同样记录 `unavailable`；之后的触发可以启动新的评估。策略变更，或针对过期策略做出的决定，记录 `unavailable`，并立即按当前版本重新排队该批次。

`evals` 健康条目报告过去一小时内未解决的 unavailable 决定。`scripts/dsh-superagent status` 会包含该错误。

只有当该 unavailable 决定不满 24 小时、仍是其线程上最新的决定、未被忽略，并且该线程既未排队也未在评估时，面板才会请求人工关注。人可以再次评估该触发，或忽略该问题。
