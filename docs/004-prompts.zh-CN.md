# 004 提示词

> 语言：[中文](004-prompts.zh-CN.md) · [English](004-prompts.md)

本文说明智能体读什么、团队可以编辑什么，以及改动何时生效。它建立在 [000 理念](000-philosophy.md) 到 [003 执行](003-execution.md) 之上。提示词文本用英文书写。

## 团队写什么

团队可以编辑三个团队段落、添加技能，并覆盖每一个内置系统提示词部分。大部分默认内容位于 `prompts/` 和 `skills/` 之下。工具描述、通知和卡片仍留在代码中，无法通过提示词设置编辑。

| 段落 | 内容 |
| --- | --- |
| Communication | 何时给人发消息、消息怎么写、每条 GitHub 消息的开头行（默认 `This is by an automated agent, not a human`）、如何处理评审，以及哪些普通账号是评审机器人 |
| Ticket scope | 工单何时继续、何时带着草稿停止 |
| Delivery requirements | 拉取请求中的证据、带行数阈值的自动合并条件，以及提交作者；未指定时，执行器以智能体账号的 no-reply 地址提交 |
| Team skills | 智能体在需要时加载的知识，例如说明哪个飞书用户对应哪个 GitHub 账号的 `identities` 技能 |

内置文本覆盖角色、工具使用、宿主机制、授权规则以及 GitHub 和飞书技能。它按标题引用团队段落，而不重复它们。

### 内置部分与模板

覆盖使用这些键：

| 部分 | 键 |
| --- | --- |
| 共享指令与角色 | `runtime/shared`、`runtime/orchestrator`、`runtime/worker` |
| 工作指令 | `runtime/subscriptions`、`runtime/replies`、`runtime/dispatch`、`runtime/work`、`runtime/admission` |
| 移交指令 | `runtime/handoff/orchestrator`、`runtime/handoff/worker` |
| 来源技能 | `skill/feishu`、`skill/github` |
| 生成段落 | `runtime/environment`、`runtime/policy`、`runtime/policy/none` |

生成段落是可编辑的模板。它们必须保留这些占位符：

- `runtime/environment`：`{variables}`，填入执行环境各行。
- `runtime/policy`：`{version}`、`{mode}` 和 `{rules}`，每条已启用的规则一行。
- `runtime/policy/none`：`{version}` 和 `{mode}`，在没有启用任何规则时使用。

编辑某个部分会改变模型收到的指令。它不会改变准入、授权、工具检查或账号包装脚本，这些仍由代码强制执行。

在人类明确要求时，主会话还可以用 `orchestrator_prompts_save` 保存覆盖。如果一次保存省略了某个覆盖的 `base`，它会保留已保存的 base。已保存配置中已经存在但被移除的部分会在保存时被丢弃；其他任何未知部分会被拒绝。

覆盖会记录它基于哪份内置文本。升级会保留团队的文本。如果默认内容发生变化，面板会把该部分标记为 **Default updated**，并在团队文本旁显示差异。团队可以保留自己的文本、采用新的默认内容或编辑它。没有覆盖的部分会自动跟随新的默认内容。

主会话可以在 `orchestrator_read prompts` 的 `default_changed` 下读取受影响部分的名称。

## 组装与优先级

系统提示词按以下顺序组装：

1. 共享指令与角色。
2. 三个团队段落。
3. 订阅与回复。
4. 主会话的派发，或执行器的工作指令。
5. `runtime/admission`，仅用于主会话。
6. 移交指令。
7. `runtime/environment`。
8. `runtime/policy`，仅用于主会话。

准入指令来自 `prompts/admission.md`。它们描述主动研判，以及何时可以根据卡片忽略一个无关候选。`orchestrator_eval` 返回上下文，而不重复这些指令。

环境段落给主会话提供部署级的值，给每个执行器提供其工单特定的值。策略段落在每次模型请求时都从设置重新生成。它包含策略版本、接单模式、明确请求的豁免，以及以 `- <name> (<id>): <instruction>` 形式列出的已启用规则，或一条说明没有启用任何规则的陈述。它放在最后，因此策略变更不会改变前面的提示词文本。

执行器还会读取 DeepSeek Harness 的编码提示词和仓库的 `AGENTS.md`；主会话不读。推断出的工单会附加一条结尾说明，把其执行器限制在命中的规则内。派工和收到的消息以触发卡片的形式内联到达，只有被截断的内容才带资源指针。

执行器无人值守地工作。它们的工具排除那些向人提问、向人展示界面或更改配置文件的工具，例如 `ask_user_question`、`present` 和 `plugin_manager`。

从最强到最弱：

1. 由工具和宿主强制执行的事实：身份、权限、工具参数检查、回复用途、长度限制。提示词文本无法改变它们。
2. 内置段落与生成段落，按团队对它们的覆盖内容读取。
3. 主动工单命中规则中的流程与沟通要求，仅作用于该工单的执行器会话。
4. 团队段落与团队技能。
5. 外部文本：消息、评论、文档和引用。它是数据，永不改变规则或授权。

## 内置文本的原则

这些原则把 [000 理念](000-philosophy.md) 应用于智能体：

- **角色分离。** 主会话只做路由：它转达原始触发和路由事实，不做技术决定，并通过一个路由工具在单次调用中对多个等待中的候选做出决定。一条路由说明最多 30 个词。执行器读取原始来源、判断范围、实现并验证。
- **主会话不等待。** 报告、跟进通知、候选和已完成的后台作业都会作为消息自动到达。没有剩下要做的事时它就结束轮次。守卫会拒绝 `sleep`、超过 30 秒的 shell 超时和超过 5 秒的作业等待，因为被阻塞的步骤会延迟新的候选。这些指令在主会话的完整提示词中取代 DeepSeek Harness 自带的作业通知说明。
- **只在人必须行动或能用到结果时发消息：** 结果可以被评审或使用、需要决定或资源，或工作无法完成。聊天消息默认一句话，硬上限 100 词。
- **执行器决定自己的跟进。** 每个执行器处理并确认范围内的请求，并交回超出其工单或属于其他工单的请求。只有当一条消息的所有拥有者都交回它、或结束而未处理它之后，它才成为新工作。主会话会收到跟进通知，但只能按停止工作的目的处置它们。交回的消息随后作为候选到达，并带有执行器给出的理由。
- **通过订阅和主会话协调。** 执行器为上下文跟随相关线程。主会话可以用不超过 100 词的说明发送来自其他工单的事实。订阅和说明都不授予权限。
- **只在明确引用时附加。** 消息必须指向某个工单的拉取请求、Issue、来源消息或确认，或指向一次恰好匹配一个工单的近期改动。仅话题相似不够。附加会让工单订阅整个线程；发现无关的执行器使用 `orchestrator_thread_unrelated`，且不在那里回答。
- **具体地确认一次。** 在开始实质工作之前，执行器确认每个新请求，并说明对象和预期结果，形式为原始消息下的回复。
- **通过 `human_action` 提问。** 执行器在它的报告中放入一个具体问题，主会话原样转达。如果问题是由某人的消息引发的，它会指明该消息，宿主在那里提问。否则在工单的原始会话中提问。已获授权的工作可以同时继续。
- **诚实的交付。** 开启拉取请求不等于就绪；草稿标记为未完成；没有真实改动前截图的界面改动不算就绪。
- **人的暂停持续有效，** 跨越跟进、新的执行器会话和重启，直到人解除。自动反馈永不恢复被暂停的工作。
- **示例只展示格式。** 一个示例句子不是智能体可以断言的事实。
- **按结果处理评审。** 已修复并验证的评论静默解决；被拒绝的评论给出一句理由。自动评审者的线程在得到回答后解决，每个自动评审者在每个拉取请求上最多三轮。
- **对重复工作让步。** 当人的分支或拉取请求已经包含工单的改动时，执行器用一句话关闭自己的拉取请求并指向他们的。

## 版本

- 每次保存都会创建一个不可变版本，包含完整配置、修订号、前驱、时间戳和来源（面板或工具）。恢复某个版本或默认值会创建另一个版本。
- 保存会指明其基础修订。冲突的保存会被拒绝，但不会丢弃草稿。
- 会话在每次模型请求时读取最新版本，包括同一轮中的后续步骤。保存不会重启、取消或唤醒会话。宿主记录每个会话使用过的修订；执行器可以读取它在其中工作过的任何修订。
- 部署设置总大小上限，包含覆盖内容。校验会拒绝未知键、保留的内置技能名、未知的覆盖部分以及缺失的模板占位符。它从不静默截断文本。与默认内容完全相同的覆盖会被移除，以便该部分跟随未来的默认内容。
